# 人体画布加载失败兼容修复

日期：2026-11-17

## 问题

放置页收到 `body-canvas` 的 `rendererror` 后显示：

> 人体画布加载失败，请点击画布内的“重新显示”

该页面没有保存底层异常代码。代码审查发现两个会导致整块画布失败的兼容问题：

1. 本地人体 PNG 的 `onerror` 会触发整个 Canvas 的致命错误；但绘制模板本身已有同一冻结轮廓的矢量占位，不依赖该 PNG 才能完成坐标交互。
2. 人体 Canvas、照片 Canvas 和放置贴片直接调用 `wx.getWindowInfo()`。不支持该接口的旧微信基础库会直接抛错，进而触发 Canvas 失败。

本次没有把环境问题伪装为成功。真正的 Canvas 节点缺失、尺寸持续为零或 2D 上下文绘制异常仍会进入可恢复错误状态。

## 修复

- 新增统一的安全设备像素比读取：优先 `wx.getWindowInfo()`，回退 `wx.getSystemInfoSync()`，都不可用时使用 1。
- 当 Canvas 节点不支持 `createImage()` 时继续绘制冻结的人体矢量模板。
- 当本地人体 PNG 加载失败时保留矢量人体，不触发 `rendererror`。
- 用户点击“重新显示”时清理失败图片缓存并重试 PNG；恢复图片后原位重绘。
- 同一安全 DPR 逻辑同步用于照片框选、人体放置贴片和特殊部位 Canvas，避免这些页面出现相同基础库兼容错误。

## 放置页专项复核（2026-11-17）

继续排查后确认，放置页已经不再嵌入旧 `body-canvas`，而是使用稳定的本地人体 PNG 和一个独立的病灶透明 Canvas。用户仍看到“人体画布加载失败，请点击画布内的‘重新显示’”时，说明运行的是旧构建、旧热重载页面或旧体验包；当前放置页源码不存在这句提示。

同时发现页面 watchdog 与任务记录不一致：记录声明首次等待 8 秒，源码实际仍为 1.2 秒。这会让慢设备上的合法首帧被过早判为失败。现已修正：

- 首次等待恢复为 8 秒。
- 首次超时或第一次真实 Canvas 绘制错误会自动重建一次 Canvas，并保持本地人体底图可见。
- 自动恢复过程中不再显示阻塞性的失败文案。
- 只有一次自动恢复仍失败时，才提供可点击的重试状态。
- 成功首帧会清除错误、等待和自动重试状态。
- 人体工作区尺寸测量持续为零时，使用实际窗口尺寸计算同一工作区视口，不留下空白页面。
