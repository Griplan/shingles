# 06 用户感知等待

## 已有反馈

当前页面并非完全无反馈：

- 选图后立即显示“正在准备照片…”；
- 上传阶段显示“正在上传…”；
- 框选松手后同步进入 `segmenting`，显示“正在 AI 分析…”；
- 等待期间保留原照片；
- Mask 图片加载并绘制完成后才启用“确认识别范围”；
- 候选切换显示“正在切换结果…”；
- 失败时保留照片并提供重新圈选、精细调整和返回手动标注。

实现中没有虚假百分比进度。页面对“AI 分析”和“正在切换结果”使用同一轻量状态，没有伪造动画完成度。

## 主要等待

| 场景 | 框选松手到 Mask 可交互 | 用户感受判断 |
| --- | ---: | --- |
| 本机冷启动 | 约 2.38 秒 | 明显等待；冷模型首次编码占主导 |
| 本机暖启动 | 约 0.76 秒 | 可感知，但接近常见网络操作等待 |
| 腾讯云 | 约 3.82 秒 | 明显等待；CPU 推理占主导 |
| 客户手机 | `NOT_MEASURED` | 需真机确认，不能直接套用上述数值 |

上传本身约 0.15 秒；候选切换约 0.02 秒；放置页可交互约 0.02 秒。用户感觉“整条流程慢”主要会集中在框选后的 AI 等待，而拖动不跟手则属于另一个高频 Canvas 路径。

## 计算慢与反馈不足的区别

- 计算慢：云端 3.7–3.8 秒真实推理。现有文字反馈及时，但等待时间客观较长。
- 主观等待放大：照片虽然保留，但页面只有一个短状态文字；没有阶段说明，也没有可取消的单次推理进度。不能通过虚假百分比解决。
- 交互不跟手：框选每个移动事件都重绘。其实际屏幕表现尚需真机测量。
- 候选切换：已有明确反馈，约 21 ms，不是主要等待来源。
- 放置调整：拖动不发请求，不出现后端等待；已有 RAF 和缓存贴图。

## 可以改善体验但不改变算法的方向

1. 在进入 AI 分析后显示“正在定位局部区域 / 正在计算轮廓 / 正在准备预览”等真实阶段，阶段必须由实际状态触发。
2. 提供取消当前 AI 请求的明确入口，并保持服务端 operation/revision 失效保护。
3. 冷启动时在服务启动阶段预热模型，或在 readiness 中暴露预热完成状态；预热不得与用户请求争抢单 Worker。
4. 优化框选 Canvas 后，手机触摸会更接近普通贴纸交互。
5. 评估有界特征缓存，减少同图重复编码；必须先验证内存与等价性。

本轮不实施这些 UI 或业务修改。
