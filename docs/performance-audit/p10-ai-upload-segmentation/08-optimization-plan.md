# 08 优化方案与验证门槛

本轮只提出方案，没有实施性能重构。

## P1-A：会话级有界 MobileSAM 特征缓存

修改范围：后端 AI 推理模块。

建议：

- 缓存键包含分析会话所有权、`photo_id`、校正 RGB 摘要、实际整数 `crop_xyxy`、模型权重 SHA、预处理版本、device 和 dtype。
- 同 crop 的不同框/点提示可复用图像 embedding；框变化导致 crop 变化时必须 miss。
- 只缓存 embedding，不缓存旧提示的最终 Mask 结果。
- 保留 operation、revision、photo mismatch、会话删除和超时检查。
- LRU + TTL + 明确总张量预算；换图、删除、过期、模型变化时清理。
- 初始实验建议每会话最多 1–2 份、全局最多 4 份，先以内存测量决定真实预算；这些不是生产承诺。
- 所有缓存操作仍在单 Worker 锁内，不增加并发模型执行。

风险：

- embedding 每个裁片至少约 4 MiB，但活动张量、拷贝和 PyTorch 中间峰值远高于该值。
- 当前云端 dermatome cgroup 峰值约 797 MB，MemoryHigh/MemoryMax 仍需按现有部署约束核验。
- 多用户、多局部框和 LRU 淘汰可能产生竞态或内存抖动。

验收：

- 同 crop 新旧 Mask 逐像素一致，MultiPolygon 孔洞和小片一致。
- 同图改框命中/未命中符合缓存键。
- 换图、删除、过期后无跨会话读取。
- Linux 300 万像素与多局部框下测量 RSS、峰值、淘汰和 CPU。
- 云端低负载同输入前后响应逐字段一致。

## P1-B：照片 Canvas 按帧合并与布局缓存

修改范围：仅小程序前端。

建议：

- 手势开始或布局稳定时缓存 node、context、尺寸和 bounding rect。
- 在 resize、show、滚动、节点替换、`layoutRevision` 或页面隐藏时使缓存失效。
- 用一个待绘制帧合并多个 `touchmove`；绘制前保留 event serial、gesture epoch 和 `touchcancel` 检查。
- 将静态照片/Mask 与动态框/点拆层，移动时只重画动态层。
- `setData` 仅在语义状态变化时提交，避免每帧调用。

风险：

- 缓存 left/top 后若页面滚动或安全区改变，可能产生坐标偏移。
- 拆层与 RAF 若处理不当，会出现旧帧覆盖新照片或候选 Mask。

验收：

- 320/375/430 px 及折叠双栏的框、点、Mask 坐标不变。
- 快速拖动、touchcancel、换照片、候选切换、resize、show/hide 无旧帧残留。
- 同数据比较每个拖动只产生一次实际绘制。
- 手机原生 trace 测量掉帧、触摸到屏幕延迟和长帧。

## P1-C：冷启动与真实反馈

修改范围：后端生命周期和轻量前端状态。

建议：

- 评估服务启动后模型预热；预热完成前 readiness 明确标记。
- 不增加并发推理，不在用户请求中重复加载模型。
- 将现有“正在 AI 分析”拆为由真实状态触发的阶段，不显示虚假百分比。
- 提供可取消请求，并由 operation/revision 保证迟到结果不会覆盖新状态。

风险：

- 预热会提高服务启动时间与常驻内存。
- 过早把 readiness 标为完成可能把请求送往尚未预热实例。

验收：

- 预热前后同输入 Mask 等价。
- readiness 与模型实际可服务状态一致。
- 云端启动时间、常驻 RSS、首次请求耗时与 OOM 观察完整。

## P2：后处理性能

在保留全部小片和孔洞的前提下，分析轮廓提取、Shapely 像素并集和序列化占比。只允许优化实现，不允许降低拓扑精度。当前数据不足以给出安全收益，暂不实施。

## 不需要优先处理

- 候选切换：约 21 ms。
- 人体放置初始化和拖动：已有缓存/RAF，调整期间无后端请求。
- 上传网络：当前测试约 0.15 秒，不是主要秒级等待。

## 推荐顺序

1. 先做独立 Linux 同架构 embedding 内存与缓存等价实验，不上生产。
2. 完成照片 Canvas 前端最小改造并做微信原生 trace。
3. 依据真机与云端数据决定是否预热模型和拆分阶段反馈。
4. 最后再评估后处理优化。
