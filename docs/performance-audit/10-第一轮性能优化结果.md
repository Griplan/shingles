# P6 第一轮性能优化结果

日期：2026-11-03。本轮状态见唯一台账 [task.md](../../task.md)。**两项代码优化与本地等价性/性能回归已完成；微信原生、手机验收 NOT_RUN，未部署云端、未上传体验版。** 本文和 `p6/` 是新记录，不覆盖 P5 的10份中文报告和旧测量。

## 结论与范围

仅修改两个产品文件：

- [annotation-geometry.ts](../../miniprogram/utils/annotation-geometry.ts)：给不可变人体环建立64个 Y 区间的保守边索引，减少 `pointInBody` 中与当前 Y 不可能相关的边扫描。
- [dermatome_matcher.py](../../backend/app/services/dermatome_matcher.py)：在一次 `evaluate` 的每个 view 中构造一次完整候选图谱并集，显式传给逐片与汇总 `coverage`。

没有更换人体、改图谱、简化轮廓、删除小片/孔洞、改面积阈值或匹配公式；没有缓存“上次校验通过”的结论。松手仍检查全部几何；确认仍从照片原始轮廓和最终参数重算并执行完整校验。未实现 AI 特征缓存或照片 Canvas 重构。

## 1. 真实调用链和瓶颈

代码与 P5 审计一致。`placement-overlay.touchEnd → placement.onDrag(end) → update(complete=true) → PlacementSessionStore.update → transformPhotoPolygonToBody → validatePlacementGeometry → pointInBody → locatePoint` 在松手同步执行。滑杆 `scaleChanged/angleChanged`、拖动中 `finishAdjustment/onHide` 走同一完整路径。复杂轮廓的每个顶点、每个边界相交切分区间内点都反复扫描1563/1487个人体源轮廓顶点。

`placement.confirmPosition → PlacementSessionStore.confirm → AnnotationSessionStore.commitPlacement` 再次执行 `preparePhotoGeometry → transformPhotoPolygonToBody → validatePlacementGeometry`，深比较正式几何与预览后才写入 V2。这个重复是最后一道信任检查，本轮**保留**。待编辑 revision、source 过期、会话版本、目标模板、视图和幂等确认检查均未改。

连续 touchmove 仍只更新相似变换和缓存贴片，不做全量变换/包含校验；页面已有单帧调度。本轮没有重构事件、绘图层或 setData。残留耗时还包括照片轮廓拓扑校验和保存序列化，不将其隐去。

后端 `evaluate → candidates_for(view) → 每片 coverage + 标注并集 coverage`：原来每次 `coverage` 均 `unary_union` 同一候选列表。5对象时该完整图谱并集重复6次，20对象时21次。候选分组内的小并集及用户标注并集是不同运算，仍保留。`load_dataset` 每请求读取/校验图谱、人体、SHA256、版本的行为也保留。

## 2. 等价优化及缓存边界

### 人体边索引

- `locatePoint` 原始通用函数不变。`pointInBody` 仅将人体环查询转给 `locateBodyPoint`；少于32顶点、不完全冻结或坐标不合法的环仍使用原函数。
- 环必须 `Object.isFrozen(ring)` 且每个点冻结。WeakMap 用实际 ring 对象作键；不同模板/视图/内容对象各自建立索引。可变/浅冻结输入每次读取现值，不缓存；冻结 outer 下更换 holes 也会重新按当前 holes 查询。
- 每条边按 `[minY−EPS,maxY+EPS]` 放入所有相交桶，顺序保持原遍历顺序。查询只缩小候选边集合；原 `onSegment`、射线交点表达式和 EPS=1e−12 完全复用，没有扩大人体。
- 索引不保存病灶/变换/合法性结论，不需要复用 revision 通过状态，位置/旋转/缩放每次仍进行完整验证。WeakMap 不延长过期环的生命周期；无全局无限版本列表。
- `validatePlacementGeometry` 的自交、凹面、整条边区间、人体孔洞包围、病灶孔洞和小片检查全部原样保留。它的 boundary 数组仍按原方式构造；首次索引实验已有明显收益，故没有同时叠加边索引、延迟校验或结果缓存等其他优化。

### 请求内图谱并集

`evaluate` 每个 view 的 `candidates` 建好后执行一次 union。变量只在当前请求中存在，front/back 各算各的，未来请求不共享；因此没有需要失效的跨请求版本缓存。每次仍由 `load_dataset` 验证 atlas ID/version/content SHA、body SHA 与模板绑定。

`coverage(..., atlas=None)` 保留直接调用兼容性；未传并集时按旧方式计算，传入空几何也不会误当成缺省值（显式 `is None`）。匹配排序、分组、交集、差集、去重汇总、未覆盖状态及错误响应都未修改。

2. 复用未改的 P5 页面/Store/Canvas命令适配器，10场景各3轮；同数据、尺寸、DPR、算法参数。每场景全新会话，确认只隔离网络以测真实 V2 保存，不调用生产接口。
3. 2000顶点5片5孔、375px场景各21轮；首轮标为预热，20轮进入统计。前后连续分块测量，期间不运行其他本任务重负载；没有声称随机交叉前端试验或机器完全无后台活动。
4. 后端7场景各21对，首对预热；后续20对按轮次交替 before/after 顺序。包含1/2/5/20重叠对象、未覆盖、背面及双面。总294次计时调用均为本机串行合成标注；计时前比较每组完整响应。前后模块在同一进程内，加载图谱的次数相同。
5. P50为中位数，P95用 nearest-rank `ceil(0.95*n)-1`，只在 n≥20时给出；3次探索场景不报 P95。样本仍很少，经验P95不代表稳定SLA。全量原始记录在 [summary.json](p6/evidence/summary.json) 同目录。
6. JS端包含真实函数、页面状态序列化和 Canvas **命令提交**，不含原生 raster、GPU、bridge、触摸到屏幕延迟；Python总耗时为加载校验图谱＋匹配＋响应序列化，不是 HTTP/手机等待时间。嵌套分段不能相加当总耗时。

初次20轮基线测量中途启动了等价性测试，保留为 `placement-focused-before-concurrent-not-used.json` 并排除；正式结果来自之后独立重跑。`placement-index-pilot.json`仅用于是否继续优化的单次探索，不混入正式统计。没有因结果不理想筛掉正式样本。

## 6. 内存和生命周期

- 20轮保留计时报告的测试进程，在每轮主动GC后：原版首个热轮 12.78 MiB、末轮 13.55 MiB；新版 12.92 / 13.68 MiB。增长分别 0.77 / 0.76 MiB；报告持续保留本身会增加内存。新版末轮比原版约多 0.13 MiB，包含索引、JIT和测量噪声，不能当索引独占精确大小。
- 单人体环最多64桶，边引用可跨桶，空间上界为64×边数；当前静态模型只有正背面两环，未引入病灶结果缓存。每次交互退出待调度帧为0。上述结果未发现额外线性增长，但不证明手机长期无泄漏。
- 后端同进程交替测量总峰值RSS 151.34 MiB。各组 before/after RSS范围见JSON；共享分配器高水位和两个版本共存，不是隔离峰值对照，不能宣称精确节省多少内存。请求结束不持有图谱union；没有跨请求缓存、没有新用户照片保留。

## 8. AI 图像编码缓存评估（未实现）

现有 `MobileSAM.predict` 每次调用 `predictor.set_image(rgb)`，结束 `finally: reset_image()`。`predict_regions(context_crop)`逐局部框调用该接口；多个提示在同一张照片上，只要裁片相同，理论上可复用编码特征，但现有实现不会复用。

本轮仅用一张700×460**人工合成RGB矩形**完成一次真实CPU推理，在现有reset前读取张量元数据，不保留张量；未更换权重或修改AI业务。实测特征 shape `[1, 256, 64, 64]`、float32，共 1,048,576元素、4,194,304字节＝**4 MiB/裁片**；predict结束 features确实为None。[内存记录](p6/evidence/embedding-memory.json)。本机进程峰值RSS约 826.59 MiB，包含PyTorch、权重、中间张量及分配器，不能按4 MiB或40.7 MB权重估算整体容量，也不能把M4峰值当Linux峰值。

资源依据仍是P5真实巡检（本轮未重新连接云端）：约3.64 GiB总RAM，与智枢智教共存；dermatome单Worker/单并发，CPUQuota约1CPU，MemoryHigh1280 MiB、MemoryMax1536 MiB、无服务swap。本轮未修改限制。P5本机同图热编码409～483 ms表明潜在收益；云CPU节省幅度尚未实测。

下一轮建议先在隔离环境实验，默认关闭缓存：

- 缓存键至少包含分析会话所有权、photo_id/校正RGB内容摘要、校正尺寸与EXIF/预处理版本、**实际整数crop_xyxy**、权重SHA、模型与预处理实现版本、device/dtype。解码所需 original_size/input_size一起保存。禁止把不同照片、用户、正向处理版本的特征混用。
- 同crop不同点可复用图像编码；框变化或框外前景点使上下文crop扩张则miss；同照片新增局部框独立编码。提示revision仍约束结果，不把旧预测结果复用成新结果。笔刷仅改Mask、不改原图时，特征是否保留可独立决定，确认结果仍有自己的版本。
- 初始实验可尝试全局最多4份/16 MiB张量、每会话最多2份、TTL最多5分钟且不超过会话剩余30分钟、LRU淘汰；必须同时计入活动张量和克隆峰值。此处只是待验证预算，不是生产容量承诺。8～16份缓存会分别占32～64 MiB，还需额外拷贝/元数据/推理峰值，当前1.5 GiB上限不能忽视。
- 保留单推理锁、busy429、请求截止和operation/revision检查；取消/更换照片、会话删除/过期、模型变更时清理缓存。删除与编码并行时，完成编码后必须再次检查会话存在/未失效，防止已删照片的特征重新进入LRU。
- 不将特征落盘或输出日志，不跨会话命中。先测试同crop新旧Mask逐像素一致、孔洞和小片一致，再测Linux 3MP图片/多局部框峰值RSS、LRU和TTL回收；未证明峰值安全前不得上线。

本轮只有内存元数据观测，无缓存命中率、Linux带缓存基准或医学准确率结论。
